这里重写精读《Vector Policy Optimization: Training for Diversity Improves Test-Time Search》。论文入口：arXiv:2605.22817。作者来自 MIT、Improbable AI Lab、MIT-IBM Computing Research Lab、Sakana AI 等机构。本文提出 VPO，把后训练目标从单一标量奖励扩展到向量奖励覆盖，核心动机是让模型为 test-time search 生成多样且互补的候选，而不是在训练阶段过早塌缩到单一答案模式。

1. 背景和问题

当前 LLM 后训练常围绕单个标量 reward 优化，例如 GRPO、RLVR、DPO 或其他偏好优化方法。标量 reward 的好处是简单直接：每个回答得到一个分数，策略更新把概率质量推向高分答案。但当系统在测试时会采样多个候选，再用 verifier、unit test、reward model 或搜索过程选择最佳结果时，训练阶段的模式塌缩就会成为问题。模型如果只学会给出同一种高概率答案，best-of-k 或 pass@k 的上限会受限，因为多次采样只是同一答案的微小变体。 VPO 的核心问题是：如果 exploitation 已经由 test-time search 负责，训练阶段是否应该更重视 exploration 和 functional diversity？这和推荐系统中的多目标候选生成很像。一个排序模型如果只优化单一点击率，可能忽略长期留存、内容多样性、风险约束或用户不同偏好；一个后训练 LLM 如果只优化单一 reward，也可能丢失多条可行推理路径。VPO 把这个问题形式化为 reward vector，而不是单个 reward scalar。

Figure 1 展示 VPO 的动机：左侧是二维目标空间中的 Pareto frontier，标量 GRPO 往往把样本推向某个单一权重方向，而 VPO 希望覆盖多个 trade-off；中间 LiveCodeBench 曲线显示，随着 best-of-k 增大，保留多样候选的策略能持续获益；右侧开放式搜索任务说明，在 AlphaEvolve / OpenEvolve 这类系统中，模型不是一次回答结束，而是要为搜索过程提供可变异、可选择的候选。图的重点不是表面文本多样，而是功能多样：候选之间应在 reward components 上互补。 这篇论文值得重写，是因为旧笔记把它概括为“训练多样性改善搜索”，但没有解释多样性到底指什么。VPO 的多样性不是换词、换语气或随机采样温度，而是不同候选在 reward vector 上专长不同。例如代码题可以有多个 test case，数学或多跳 QA 可以有多个子目标，工具调用可以有多个环境状态，推荐可以有多个 persona 或业务指标。VPO 要求训练时承认这些目标维度，而不是在进入策略更新前就把它们压成单一分数。

VPO 还回应了一个常见误区：后训练中的“更强”不一定等于“单次答案最高分”。在有测试时搜索的系统里，模型更像候选生成器，而不是最终决策器。候选生成器的目标应包含 coverage、novelty 和互补性；最终选择由 verifier 或搜索过程完成。若训练阶段已经把所有概率质量压到一种答案，测试时搜索就失去意义。这个逻辑和 beam search 中 diverse beam、推荐中的 candidate diversity、规划中的多路径搜索都相通。 VPO 的背景也与 AlphaEvolve / OpenEvolve 这类开放式程序搜索有关。这类系统会反复采样、变异、评价候选程序。若底层模型只能给出相似候选，即使搜索框架很复杂，也探索不到远处解。VPO 试图从训练阶段改善候选分布，使模型输出在 reward space 上天然分散。

补充背景：VPO 的关键不是“让回答更丰富”，而是承认很多系统在测试时本来就会搜索。代码生成会跑 unit tests，工具调用会执行环境检查，多跳 QA 会用 verifier 或 reward model 选候选，推荐系统也会先生成候选再重排。若训练只把概率质量推向单一标量最优答案，测试时搜索看到的是很多相似样本，预算被浪费。VPO 把训练目标改成覆盖 reward vector，本质上是在为后续搜索准备有差异且仍然有价值的候选集合。

2. 方法

2.1 从标量 reward 到向量 reward

VPO 假设每个候选回答 $y_i$ 得到的不是标量 $r_i$，而是向量 $\mathbf{r}_i\in \mathbb{R}^d$。维度可以来自 test cases、多个 reward models、多个用户 persona 或多个任务指标。传统做法会先把向量加权成 $s_i=\mathbf{w}^\top \mathbf{r}_i$，然后用 GRPO 之类方法更新策略；VPO 则在一次 prompt 的候选集合内部采样多个权重向量，让不同候选在不同 scalarization 下被认可。 公式清单包括三项。第一是 reward vector：$\mathbf{r}(y)=[r_1(y),r_2(y),\ldots,r_d(y)]$。第二是权重采样：$\mathbf{w}\sim Dirichlet(\alpha)$，它表示不同目标 trade-off。第三是 advantage estimator：对候选 $y_i$，在不同 $\mathbf{w}$ 下计算 $\hat{A}(y_i\mid \mathbf{w})$，再把那些在某些权重方向上表现好的候选推高。与 GRPO 只围绕一个 group mean advantage 不同，VPO 让一个 prompt 下的多个答案可以各自服务不同目标方向。

2.2 VPO 的训练流程

训练时，模型对同一 prompt 采样 $m$ 个候选，得到 reward matrix $R\in \mathbb{R}^{m\times d}$。如果用标量 GRPO，通常会把每行 reward vector 压成一个数，再比较候选好坏；VPO 则采样若干 Dirichlet 权重，对每个权重计算所有候选的 scalarized reward，并识别在该权重下表现较好的候选。这样，一个候选即使不是全局平均最高，也可能在某个目标组合上有价值。

Figure 2 展示 VPO 的核心计算。左侧模型对同一输入采样多个 rollout；中间得到每个 rollout 在多个 reward component 上的分数；右侧对不同 Dirichlet 权重进行 scalarization，并把 advantage 分配给在对应权重下更好的候选。图下方的公式直观说明：VPO 估计的不是“这个答案是否总体最高分”，而是“这个答案是否在某个目标权衡下有独特价值”。这正是 test-time search 需要的候选集合性质。

这张图表的重点是功能多样性而非表面改写：只有当候选在 reward vector、best@k 或搜索预算下产生互补价值时，VPO 的训练目标才算被实验支撑。### 2.3 为什么它能改善 best@k

Best@k 的前提是系统会看多个候选。如果候选高度相似，$k$ 增大并不会带来真正搜索；如果候选覆盖不同思路，verifier 或任务奖励才有机会从中挑到更好的结果。VPO 在训练阶段鼓励 reward-space coverage，等价于提前为搜索过程准备可探索的分支。它不一定提升 pass@1，因为 pass@1 更偏向单一最优模式；但当 $k$ 增大时，多样候选的优势会显现。这也解释了为什么

VPO 和温度采样不同。提高采样温度会增加表面随机性，但不保证候选在关键目标上互补，甚至可能产生更多低质量答案。VPO 的多样性受 reward vector 约束：候选必须在某些维度上有高分，才会被训练强化。因此它追求的是“有用的多样性”，不是无结构的随机性。

2.4 和推荐多目标排序的联系

如果把 prompt 看成用户请求，把候选回答看成候选 item 或候选策略，VPO 与推荐系统很接近。推荐中的 reward vector 可以包含点击、转化、停留、满意度、风险、库存、长期价值和多样性。传统单标量优化会把这些目标在训练前压成一个业务权重，而

VPO 式训练会保留多个目标方向，让模型生成覆盖不同 trade-off 的候选，再由后续重排、约束求解或在线策略选择。这个思想对 LLM reranking、RAG candidate generation 和 agent planning 都有迁移价值。当然，推荐系统的 reward 往往延迟、带偏、受曝光影响，不像 benchmark test case 那样干净。若直接套 VPO，需要先解决 reward vector 的可观测性和可信度。可以从离线多 persona 评价、多个 reward model、反事实模拟或规则约束开始，而不是直接用线上业务指标。

2.5 适用边界

VPO 最适合有 test-time search 或 verifier 的系统，例如代码生成、工具调用、复杂 QA、自动程序搜索、agent planning。如果产品场景只允许一次低延迟回答，且没有后续候选选择过程，VPO 的收益会下降，甚至可能牺牲 pass@1。它也要求 reward components 足够有意义；如果向量维度只是噪声或高度相关，采样不同权重不会产生真实的功能多样性。

2.6 Advantage estimator 的直觉

在 GRPO 中，同组候选通常围绕平均 reward 计算 advantage，高于平均的答案被强化，低于平均的答案被抑制。若 reward 是单标量，这会鼓励所有候选朝同一个高分模式移动。VPO 改成多个 scalarization 后，一个候选即使平均分不是最高，也可能在某个 $\mathbf{w}$ 下具有正 advantage。训练因此保留了 specialized candidate，而不是把它当成低分噪声删除。

2.7 Dirichlet 权重的意义

Dirichlet 分布用于在 simplex 上采样目标权重。若 $\alpha$ 较小，采样会更偏向极端目标，鼓励候选专攻某些 reward component；若 $\alpha$ 较大，权重更均匀，候选更接近平衡方案。这个超参数决定 diversity 的形态。推荐系统类比中，小 $\alpha$ 可能生成面向不同用户群或业务目标的候选，大 $\alpha$ 则更像寻找折中方案。

2.8 Diversity 不是无约束随机性

VPO 的 diversity 受 reward vector 约束，候选必须在至少某些维度上表现好。若一个候选只是风格不同但所有 reward component 都低，它不会被强化。这个设计避免了高温采样常见的问题：输出很多不同但没用的答案。对代码任务来说，功能多样性可能意味着通过不同 test subset；对推荐任务来说，可能意味着覆盖不同 persona 或约束组合。

2.9 与 Multi-RLVR / GDPO 的关系

Multi-RLVR 也关心多奖励或多任务，但

VPO 更强调同一 prompt 下候选集合的 coverage。GDPO 等方法可能直接加入 diversity regularization，但如果 diversity 没有和 reward components 对齐，可能鼓励表面差异。VPO 的优势在于把 diversity 建立在可解释的 reward vector 上，使训练信号与 test-time search 的选择标准一致。

2.10 训练成本

VPO 需要对每个候选计算多个 reward component，这比单 reward 更贵。若 reward 来自 unit tests，成本可能可控；若来自多个 LLM judge，成本会很高。训练时还要采样多个权重并计算 advantage。实际部署需要权衡：VPO 节省的是测试时无效采样和搜索停滞的成本，增加的是训练阶段多维评价成本。

2.11 安全约束

多样候选可能包含更多边界行为。若 reward vector 没有安全维度，模型可能生成在任务分上高但不安全的候选。因此安全、合规、一致性最好也是 reward vector 的一部分，或者在 test-time verifier 中作为硬过滤。VPO 不自动解决安全问题；它只是让训练保留多目标覆盖。

2.12 公式审计：向量奖励如何进入策略更新

VPO 的核心变量包括候选集合 $\{y_i\}_{i=1}^m$、reward matrix $R\in\mathbb{R}^{m\times d}$、权重向量 $\mathbf{w}\sim Dirichlet(\alpha)$ 和在不同权重下计算的 advantage。传统标量化会先给每个候选一个固定分数 $s_i=\mathbf{w}^\top\mathbf{r}_i$，再围绕单一排序更新。VPO 则采样多个 $\mathbf{w}$，让同一个候选在某些目标方向上可以得到正向训练信号。

这个区别会改变组内竞争关系。GRPO 里，一个候选只要低于组平均，就可能被压低；VPO 中，它如果在某个 reward component 或某个 trade-off 上突出，就不应被当作噪声删除。这样训练出的策略更像候选生成器，保留多个功能方向，而不是只学习一个最安全的平均答案。

2.13 Reward vector 的构造比算法名更重要

VPO 是否有效，首先取决于 reward vector 是否真实表达任务差异。代码任务可以把 test case 或 test suite 分组作为维度；多跳 QA 可以把证据链、最终答案、引用一致性分开；工具调用可以把环境状态、执行成功、成本和安全约束分开；推荐可以把点击、转化、满意度、多样性和风险拆开。若这些维度高度相关或噪声很大，Dirichlet 采样也不会产生有效 diversity。

因此复现时不要先调 $\alpha$，而要先审计 reward components。每个维度都应有独立含义、可重复计算、可被 verifier 检查，并且和最终选择过程有关。否则 VPO 可能只是在噪声维度上鼓励分散，带来更高采样成本而不是更好 best@k。

2.14 与推荐多目标候选生成的对应关系

在推荐系统中，VPO 可以理解为训练一个多目标候选生成器。线上最终排序通常会用多目标融合和约束求解，但候选生成阶段如果已经塌缩，就算 reranker 再强也只能在狭窄集合里选择。VPO 式训练让同一用户请求下的候选覆盖不同目标方向，例如短期点击、长期满意、内容多样、风险可控或新颖探索。

迁移时要特别注意反事实偏差。推荐 reward 往往来自曝光后的用户行为，不同候选并没有被同等观察。比起直接用线上点击当 reward vector，更稳的起点是离线 persona 评价、人工偏好维度、多 reward model 或模拟环境。等候选集合确实改善 reranker 上限后，再考虑小流量线上验证.

论文指出，VPO 在较少 rollout 下能超过给 GRPO/GDPO 更多 compute 的设置。这一结果支持一个判断：问题不是候选数量，而是候选覆盖。更多 rollout

如果来自已经塌缩的策略，只会重复相似答案；较少但经过 reward-vector 训练的候选，反而能覆盖更大的有效搜索空间。这个结论对 LLM agent 系统很重要，因为真实系统的 token 和工具调用预算有限，不能无限采样。

3.5 风险和边界

VPO 的实验仍是受控任务。真实生产 LLM 后训练面临 reward hacking、安全一致性、多目标权重漂移等问题。Reward vector 维度越多，越需要防止模型专门钻某一维漏洞。多样候选也可能增加不安全输出概率，因此 test-time verifier 必须可靠。对推荐系统来说，多样性还可能和用户体验一致性冲突：用户希望系统稳定理解偏好，而不是每次给出完全不同方向的候选。

3.6 Best@k 曲线的读法

VPO 的核心证据应看曲线斜率而不是单点。如果 best@1 不高但 best@k 持续上升，说明候选集合中有不同有效方案；如果曲线很快 plateau，说明采样更多没有新信息。论文结果显示

VPO 随 k 增长更能释放收益，这正符合训练目标。

3.7 Compute 对比

论文强调 VPO 不是靠更多 rollout 获胜。给 GRPO/GDPO 更多 compute 后仍不一定追上

VPO，说明候选分布的结构比采样数量更重要。这个结论对实际系统很关键，因为生产环境常常无法把 k 提得很高；如果候选质量结构更好，较小 k 就能获得搜索收益。

3.8 复现实验检查清单

VPO 的实验要同时看 pass@1、best@k、diversity 和 compute。若 best@k 提升但 pass@1 大幅下降，说明训练可能牺牲了单次质量；若 diversity 提升但 best@k 不升，说明只是表面分散；若需要极大 k 才有收益，生产预算可能不允许。理想结果是较小 k 下就能看到曲线斜率改善，并且 compute 对比公平。

还要检查 baseline 是否给足预算。论文强调 VPO 在更少 rollout 下能超过给 GRPO/GDPO 更多 compute 的设置，这一点比单点最高分更有价值。它说明瓶颈不是采样数量，而是候选分布结构。复现时应固定模型、数据、reward 评估次数和 verifier，再比较策略差异。

3.9 安全与失败案例

多样候选会扩大输出空间，也可能扩大风险空间。若 reward vector 没有安全维度，模型可能生成任务分高但不合规的候选；若 verifier 只看功能正确，风险会在 test-time search 中被放大。VPO 的生产落地必须把安全、合规和一致性作为 reward component 或硬过滤，而不是事后检查。尤其在工具调用和 agent planning 中，多样探索可能触发更多边界操作。

4. 总结

4.1 我的判断

VPO 的价值在于把 test-time search 的存在提前纳入训练目标。它提醒我们：如果部署时会用 best-of-k、verifier、程序搜索或多候选重排，训练时就不应只优化单一高分答案。这个思路对代码、Agent、RAG 和推荐多目标候选生成都值得关注。

4.2 工程启发与复现建议

复现时应先构造可信 reward vector，例如按 test case、子任务、persona 或多个 reward model 分维度打分。然后比较 pass@1 与 best@k 的 trade-off，不要只看单次回答。若迁移到推荐或 RAG，可以让模型生成多个候选 query、检索计划或解释，再由后续 verifier/reranker 选择。

4.3 局限与后续跟进

局限包括：reward vector 构造成本高；无 test-time search 的低延迟场景收益有限；多样性可能带来安全和一致性风险；大规模生产后训练仍需更多验证。后续应关注代码开源、reward-vector 数据格式、与 GRPO 在相同 compute 下的公平比较，以及

VPO 是否能改善真实 agent benchmark 的成功率而非只改善离线 best@k。

4.4 我会如何落地

我会优先在代码生成或工具调用中试

VPO，因为 reward vector 容易来自 test cases 或环境检查。推荐系统中可先离线构造 persona-based reward vector，再观察候选集合是否提升后续 rerank 的上限。不要直接用线上多目标业务指标训练，除非已有可靠反事实估计。

4.5 后续问题

最关键问题是 reward vector 如何构造、是否会被模型钻空子、以及

VPO 与 verifier 的配合。若开源代码发布，应重点看 advantage estimator、Dirichlet 超参数、reward normalization 和 diversity metric 实现。

4.6 后续观察清单

后续最值得跟踪的是代码开源后 advantage estimator 的实现、Dirichlet $\alpha$ 的敏感性、reward normalization 和 verifier 配合方式。VPO 的思想很适合有 best-of-k 或搜索预算的系统，但它不是通用单次回答优化器。判断是否采用时，应先问产品链路是否真的会看多个候选，以及 reward vector 是否足够可信. 补充一点，VPO 也提醒后训练评估不能只看一个平均分。只要部署链路包含多候选搜索，就应该单独报告候选间有效差异、verifier 命中率、失败样本类型和安全过滤比例。否则所谓 diversity 可能只是文本表面变化，无法证明它真的提升了搜索空间。
